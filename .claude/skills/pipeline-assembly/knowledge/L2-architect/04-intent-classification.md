# 意图识别与受理分类（总装专属）

> 层：L2-architect ｜ 读者：总装 ｜ 状态：v0.1 初稿，随实际会话积累完善

## 五类需求

| 分类 | 一句话定义 | 用户话术信号（示例） |
|---|---|---|
| 组装新链路 | 把业务需求拼成可运行管道 | "我要检测停车场拥堵"、"摄像头拍到打架要告警"、"做一个识别老鼠的链路" |
| 咨询 / 系统介绍 | 问系统能干什么、怎么用 | "系统能识别什么"、"web_lab 怎么用"、"什么是 large_only" |
| 已有链路调参 | 对已跑的链路改参数 | "抽帧间隔改成 1 秒"、"告警冷却太短了"、"把 conf 调低一点" |
| VLM 提示词 | 改大模型研判的提示词 / 词表 | "提示词让它顺便识别吸烟"、"加一个 smoking 动作" |
| 改模块需求 | 要动核心模块代码 | "composer 加个新判定模式"、"人脸底库要支持动态增删" |

## 路由结果

| 分类 | 处理路径 | 产出 |
|---|---|---|
| 组装新链路 | 需求澄清 → 方案设计（闸门①）→ 派发组装工 | 交付包（方案 + 资源 + 壳 + 测试 + 清单） |
| 咨询 / 系统介绍 | 直接答（读 L1 知识） | 说明文字，不产生代码 |
| 已有链路调参 | 定位 spec → 改参数 → 建议（涉及告警 / 模式变化时需确认） | 更新后的 spec + 说明 |
| VLM 提示词 | 先定词表 → 写提示词候选 2–3 版 → 标注依赖实测 | 提示词稿 + target_actions 建议 |
| 改模块需求 | 升级通道：停住 → 说明改动点 / 理由 / 影响面 → 等单独批准 | 批准后转交相应负责人 |

## 边界情况

- **多意图夹带**：一个需求含多个分类（如"加吸烟识别顺便讲讲系统能力"）→ 按主导意图归类，
  次要意图在交付中附带处理或明说"不在本次范围"。
- **信号不足**：走需求澄清（追问设备 / 分辨率 / 路数 / 目标类别 / 告警需求 / 预算 / 数据来源），不硬猜。
- **组装 vs 调参**：已有链路存在（spec 已存 / 已有产物）→ 调参；没有 → 组装。
