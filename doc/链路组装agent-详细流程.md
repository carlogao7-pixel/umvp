# 链路组装 Agent —— 详细流程（设计）

> 状态：**初稿 v1.0**（2026-08-11）。
> 定位：与《链路组装agent-职能与边界》配套。那份文档回答"能做什么、不能做什么"；
> 本文回答"一个需求进来，从受理到交付一步步怎么走"。两者互补，本文是流程的可读展开。
> 覆盖对象：总装（pipeline-architect）+ 组装工（pipeline-assembler）两个 agent 的完整协作流程；
> 也覆盖咨询 / 调参 / VLM 提示词 / 改模块四条非组装路径。
> 读者：项目开发者，以及需要理解 agent 运作方式的任何人。
> 关系说明：本文是流程的**静态快照**；agent 运行时依据是知识库 `.claude/skills/pipeline-assembly/`
> （INDEX.md + 分层文件）与两个 agent 提示词。口径发生漂移时，以知识库 / 代码 / CLAUDE.md 为准，
> 维护规则见 §11。

---

## 0. 一张图：需求从进来到交付

```
业务需求（自然语言 / spec JSON / 咨询问题）
   │
   ▼
[总装] 0 受理分类
   │  ├─ 咨询 / 系统介绍 ──► 直接答（读 L1 知识）──────────────► 结束（说明文字，无代码）
   │  ├─ 已有链路调参 ──► 定位 spec → 改参数 → 建议（告警/模式变化时需确认）► 结束
   │  ├─ VLM 提示词 ──► 先定词表 → 2-3 版候选 → 标注依赖实测 ──► 结束
   │  ├─ 改核心模块 ──► 升级通道（停住 → 说明改动点/理由/影响面 → 等单独批准）► 结束
   │  └─ 组装新链路 ──► 1 需求澄清 → 2 方案设计（闸门①：用户确认）
   ▼
[组装工] 1 解析 → 2 选链路 → 3 估算 → 4 写壳（先展示再落盘 out/generated/）
      → 5 测试 → 6 汇报
   │
   ▼
[总装] 5 质量门（不达标打回）→ 6 交付汇总
   │
   ▼
交付包 = 方案说明 + 资源报告 + 壳代码/测试壳 + 测试结果 + 已验证/未验证清单
```

组装类请求走"总装外圈 + 组装工内圈"；其余四类走分支直达结束。多链路 / 多子任务在总装
第 3-4 步拆成多条组装任务，各自走组装工内圈，最后在总装质量门合并。

## 1. 触发与受理分类（总装 · 第 0 步）

**输入**三种形态任选：
- 业务需求自然语言（最常见）；
- 已有 spec JSON（web_lab §4.1 pipeline spec 结构）；
- 咨询问题（系统介绍 / 模块答疑）。

**动作**：按五类需求判定归类（信号表见知识库 `L2/04-intent-classification.md`）：

| 分类 | 一句话定义 | 路由 |
|---|---|---|
| 组装新链路 | 把业务需求拼成可运行管道 | 进 §2 澄清 → §3 方案 → §4 派发 |
| 咨询 / 系统介绍 | 问系统能干什么、怎么用 | 直接答，不产生代码 |
| 已有链路调参 | 对已跑链路改参数 | 定位 spec → 改参数 → 建议 |
| VLM 提示词 | 改大模型研判的提示词 / 词表 | 先定词表 → 写候选 → 标依赖实测 |
| 改核心模块 | 要动 composer 四模块 / face_* / face_scan / resources.py | 升级通道（§8） |

**边界情况**：
- **多意图夹带**：一个需求含多个分类 → 按主导意图归类，次要意图在交付中附带处理或明说"不在本次范围"。
- **信号不足**：不硬猜，进 §2 澄清。
- **组装 vs 调参**：已有 spec / 产物 → 调参；没有 → 组装。

---

## 2. 需求澄清（总装 · 第 1 步）

**目的**：把零散业务描述收敛成一段"需求说明"，作为方案设计的唯一输入。

**澄清要素**（一次问全，附示例值，减少往返）：

| 要素 | 问什么 | 示例 |
|---|---|---|
| 设备 | 部署在什么机器 / 什么显卡 | RTX 3060 8G / 纯 CPU |
| 分辨率 | 输入画面多大 | 1080p / 720p |
| 路数 | 同时几路 | 16 路 |
| 目标类别 | 要识别什么（COCO 类别或自定义） | 人=0 / 车=2 |
| 告警需求 | 什么情况要告警、怎么报 | 拥堵告警 / 打架告警 |
| 预算 | 显存 / 帧率上限 | 显存 8G、实时 |
| 数据来源 | 视频流 / 图片 / 摄像头 | 16 路 RTSP |

**产物**：一段需求说明（设备 + 分辨率 + 路数 + 目标 + 告警 + 预算，缺项明标"未提供"）。

---

## 3. 方案设计与闸门①（总装 · 第 2 步）

**动作**：
1. 读决策表 `L4/10-decision-table.md`（四模式 / 人脸链路 / 监控链路）选链路；
2. 定参数初值（conf / iou / imgsz / frame_skip / check_interval / class_limits 等），说明动机；
3. 做备选方案对比（如 small_crop vs small_full 的成本与效果差异）；
4. 资源粗估：调 `ResourceEstimator` 静态层，对多路做外推，超预算给 WARNING 与 frame_skip 建议；
5. 写成方案书（结构见 §9 交付包第 1 项）。

**闸门①（硬性）**：方案书完成后**停下，等用户确认**。未确认不进入下一步。
确认内容：选哪条链路 + 备选取舍 + 参数初值 + 预算可行与否。

**产物**：经用户确认的方案书。

---

## 4. 任务拆解与派发（总装 · 第 3-4 步）

- **单链路**：直接派发组装工。
- **多链路 / 多子任务**：拆成多条任务，逐条定输入（任务说明 + 验收口径）+ 输出（各自交付包）。
- **派发机制**：
  - 【有工具时】调子 agent `pipeline-assembler`（或 Skill）；给子任务定验收口径。
  - 【无工具时】产出"任务包"：任务说明 + 组装工提示词（或按 INDEX 内联的组装工所需分层文件正文），
    交下游消费方执行。
- **改核心模块需求不在此路径**：停住，走 §8 升级通道。

**产物**：派发的组装任务（每条含验收口径），或任务包。

---

## 5. 组装工实施（组装工 · 第 1-6 步）

组装工永远只管单条链路。每一步做完即停下汇报要点；长任务先告知预计耗时。

### 5.1 需求解析（第 1 步）

从任务书 / 业务描述提取六要素（设备 / 分辨率 / 路数 / 目标类别 / 告警需求 / 预算）；
总装已澄清过的直接用，缺啥问啥。
**产物**：一段需求要点。

### 5.2 选链路（第 2 步）

读 `L4/10` 决策表 → 落四模式之一（small_only / small_crop / small_full / large_only）
或人脸链路 / 监控链路，给理由与参数初值。总装方案已定 → 直接落参数，不重复选型。
**产物**：链路选择 + 理由 + 参数初值。

### 5.3 估算（第 3 步）

- 【有工具时】调 `ResourceEstimator.estimate_pipeline(spec, streams)`：
  单模块指纹 → 按"每帧平均成本"链路聚合（VLM 节流折算 / 人脸嵌入命中后折算）→ 多路外推 →
  预算反推（给定 vram_budget → 建议 frame_skip / check_interval / 预期 FPS）。
- 【无工具时】给出"待执行命令 + 预期产出"说明（如 `python umvp/resources.py` 的用法）。
- 每项标来源（静态 / 实测 / 依赖实测）；静态 vs 实测误差 >30% 标警告；VLM 远端延迟标"依赖实测"。

**产物**：资源报告（§9 第 2 项）。

### 5.4 写壳（第 4 步）

**软边界：先展示方案再落盘**——先给方案说明 + 壳代码骨架，确认后才写入 `out/generated/`。
壳代码四样东西（模板见知识库 `L3/07-shell-templates.md`）：

| 壳代码 | 干什么 | 参照物 |
|---|---|---|
| 驱动壳 | spec → `compose()` 组装 `Pipeline` → 帧循环驱动 `step()` | `umvp/pipe/test_composer.py` 脚本化 feed 风格 |
| 接线壳 | YOLO dets 喂进管道；VLM infer 回调（真实远端 / 模拟）；告警结果落盘上报 | `VLMAnalyzer.prepare()` + infer 回调 |
| 测试壳 | 断言式测试 + 限帧 + 可视化核验产物落盘 | `tests/` 回归集风格 |
| 胶水文件 | 现有模块拼不出时才新增，逻辑最小化（先例：`crop_restore.py` 约 200 行） | `umvp/pipe/crop_restore.py` |

**产物**：`out/generated/` 下可运行脚本 + 运行命令。

### 5.5 测试（第 5 步）

- 【有工具时】三段递进：
  1. 断言式测试（脚本化 feed，秒级，纯逻辑）；
  2. 限帧真实推理烟测（确认链路通；真实推理前告知预计耗时：YOLO 秒级、三模式分钟级）；
  3. 可视化核验（落盘 annotated.png 级产物，坐标映射等靠目检的项）。
  最后跑回归集（27 断言 + 人脸 7/7 自检）确认不破坏现有链路。全程串行（`_TEST_LOCK` 约定）。
- 【无工具时】交付测试脚本 + 运行命令，标注"待执行"。
**产物**：测试结果（§9 第 4 项）。

### 5.6 汇报（第 6 步）

按五段式模板输出（没做的项如实标注"未做"，不许略过）：
1. **方案**：链路选择 + 理由 + 参数初值；有备选时一句对比。
2. **资源报告**：关键数字 + 建议；每项标来源，误差 >30% 标警告。
3. **测试结果**：断言逐条通过/失败 + 真实推理限帧数 + 可视化核验产物路径。
4. **已验证 / 未验证清单**：`| 场景 | 结果 | 备注 |`，**缺这项不算完成**。
5. **下一步建议**：要补的验证 / 要用户拍板的参数 / 建议走总装或升级通道的事项。

**产物**：交付包（§9）。

---

## 6. 质量门与交付（总装 · 第 5-6 步）

**质量门口径三项，缺一打回**：
1. 回归集全绿（27 断言 + 人脸 7/7 自检）；
2. 未验证清单诚实列全（延续 skill 风格，缺了不合格）；
3. 交付包五件齐全（方案 / 资源 / 壳代码 / 测试结果 / 清单）。

- **不达标**：打回组装工，注明缺什么（哪条断言挂了 / 哪件缺了 / 清单哪项含糊）。
- **达标**：单链路直接汇总交付；多任务合并各子产物统一汇报。

**产物**：最终交付包。

## 7. 交互节奏总表

| 位置 | 触发 | 给用户看什么 | 决策权 |
|---|---|---|---|
| 总装 受理后 | 分类不明确 / 要素缺失 | 澄清问题清单（带示例值） | 用户回答 |
| 总装 方案设计后 | 方案书完成 | 链路 + 理由 + 参数初值 + 备选对比 + 资源粗估 | **用户确认（闸门①）** |
| 组装工 写壳前 | 壳代码骨架就绪 | 方案 + 代码骨架 | 用户确认后才落盘 |
| 组装工 真实推理前 | 要跑真实模型 | 预计耗时 + 限帧数 | 用户知悉（可中止） |
| 组装工 每阶段完成 | 一个阶段结束 | 该阶段要点 | 用户可纠正方向 |
| 总装 质量门 | 组装工汇报完 | 回归集结果 + 清单 + 交付包完整性 | 总装判定，用户最终验收 |
| 换机 / 换卡 | 环境变化 | 提醒重跑 `web_lab/calibrate.py`，代码零改动 | 用户执行 |

节奏约定：**文档先行、验证闭环**（断言式测试，不接受"看起来对"）；每一步都是"小步汇报、
可纠正"，不做一次性长流程闷头跑到底。

## 8. 升级通道（改核心模块需求）

遇"要改 composer 四模块 / face_* / face_scan / resources.py"的需求：
1. **停住**，不顺着正常流程往下走；
2. 说明改动点、理由、影响面（涉及哪些现有链路 / 测试）；
3. 等**单独批准**后再动（或转交相应负责人）。

组装工无此权限，这类需求必须由总装兜住上报。

## 10. 走一遍：停车场拥堵检测需求

> 用 §0-§6 的流程把一条需求完整走一遍，作为阅读参照。

**用户**："我要做一个停车场拥堵检测的链路，16 路摄像头、1080p、8G 显存，堵了要告警。"

- **总装 0 受理**：组装新链路（有目标类别、告警需求、预算约束）。
- **总装 1 澄清**：确认帧率要求（实时）、拥堵判定口径（车辆数量上限 class_limits / 车辆静止超时）、
  目标类别 COCO 车=2。
- **总装 2 方案设计**：决策表对比——`small_crop`（YOLO 数车 + 拥堵片段裁剪送 VLM 研判）vs
  `small_only`（纯 YOLO 计数 + class_limits 判定，零远端依赖）。资源粗估：16 路外推显存
  超 8G → 给 WARNING + frame_skip 建议。方案书给出两案成本/效果差异。**闸门①等用户确认**。
- **总装 3-4 拆解派发**：单链路，派组装工，验收口径 = 交付包五件。
- **组装工 5.1 解析**：设备 RTX 3060 8G / 16 路 / 1080p / 车=2 / 拥堵告警 / 显存预算 8G。
- **5.2 选链路**：按确认的方案落 `small_only` 参数初值（conf=0.35 / imgsz=640 / class_limits="2:1,300" /
  check_interval=3.0）。
- **5.3 估算**：`estimate_pipeline(spec, streams=16)` → 单路显存/帧率 → 16 路外推 → 反推
  frame_skip=2 时帧率与显存落到预算内；VLM 不在链路，无"依赖实测"项。
- **5.4 写壳**：先展示 spec JSON + 驱动壳骨架（16 路帧循环）→ 确认后落盘 `out/generated/parking_monitor.py`
  + 测试壳。
- **5.5 测试**：脚本化 feed 断言通过 → 限帧真实推理烟测（告知预计耗时）→ 画框核验 →
  回归集（27 断言 + 7/7 自检）全绿。
- **5.6 汇报**：五段式交付包。
- **总装 5 质量门**：三项全过。
- **总装 6 交付**：交付包交用户，含"未验证场景"清单（如真实 RTSP 长稳未测）。

4. **是否需方案对比产物**：默认做（多方案成本/效果对比）；如只给单方案，本文 §9 第 1 项相应简化。
