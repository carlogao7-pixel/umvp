# 实时播放叠加（视频播放器 + YOLO 框同步）设计

> 状态：✅ 已实现（2026-09-22）｜ 落点：`web_lab/server.py`（SSE 流式运行）+ `web_lab/test.html`（播放器叠加）
> 实测：SSE 冒烟 `meta→frame×N→done`（含检测框/车牌）；停止接口 `done.stopped=true`；
> Range `206`；批量入口零回归。**顺带修复**：`/files/videos/` 未 URL 解码导致中文名视频
> 一直 404 播不了（现 `unquote` 后中文/ASCII 名均可播）。
> 目标：任务进行时同步播放视频，并把识别框实时叠在视频帧上（方案 B：真同步）。
> 追加（同日）：**解码适配**——素材多为 H.265(HEVC)/4K，浏览器不解，现按需转 H.264 缓存后播放（见 §8）。

## 1. 现状与缺口

- `test.html` 已有 `<video controls>`（播 `/files/videos/<name>`）与 `timeupdate` 帧号显示；
  但叠加层只是信息条，运行是**同步 POST**（跑完才返回），过程中前端拿不到逐帧框。
- `_send_file` 不支持 HTTP Range（206）→ 拖动进度条失效。

## 2. 核心思路：框数据流式推送 + 播放节流

浏览器本地播原视频（无需传图，带宽≈0），服务端**逐分析帧推框的数值**；前端按
`currentTime × fps` 定位帧号，把最近分析帧的框画在 canvas 上。为保证"框与画面一致"，
**播放节流**：视频只播到"已收到结果的最新帧时间"，追平后暂停等结果（缓冲），
收到新结果再续播——因此播放速度 = 处理速度（CPU 下会慢于实时，属预期）。

```
服务端: 帧循环 → 逐分析帧 SSE 推 {n, ts, dets, plates, alarms}
前端:   EventSource 收结果 → canvas 叠加；视频播到 lastResultTs 就暂停等，收到新结果再播
```

## 3. 服务端设计

### 3.1 接口

| 接口 | 说明 |
|---|---|
| `GET /api/test/pipeline_run/stream?...` | SSE 流式运行。query：`pipeline_id / video / start_time / end_time / max_frames / vlm_feedback / vlm_action`（EventSource 只支持 GET） |
| `POST /api/test/pipeline_run/stop` | body `{run_id}` → 置停止事件，循环在下一次迭代退出 |

SSE 事件（每条 `data:` 一个 JSON）：

| event | 载荷 |
|---|---|
| `meta` | `{run_id, name, fps, total_frames, start_frame, end_frame, frame_skip, stages}` |
| `frame` | `{n, ts, dets:[{cls,bbox,score,track}], plates:[{plate_no,type_name,color,score,bbox,car_bbox}], alarms:[{action,desc,conf}]}` |
| `info` | `{text}`（阶段级日志，如 VLM 研判；可选） |
| `done` | `{processed, detections, plates, alarms, elapsed, saved}` |
| `error` | `{message}` |

### 3.2 并发与停止

- 复用全局 `_TEST_LOCK`：流开始非阻塞抢锁，失败则回 `error`（"另一测试进行中"）并结束。
- 运行注册表 `_STREAMS: {run_id: threading.Event}`；`/stop` 置位；客户端断开（写失败）
  同样置位并结束循环。
- 服务端不做节奏控制（不 sleep）：结果小、播放端节流即可；`max_frames` 限流。

### 3.3 复用

- 复用 `db.load_pipeline` + `_chain_from_spec`（装配）与既有帧循环语义
  （`FrameManager.wants_frame` 门控、`yolo.infer(track=pipe.track_needed())`、`pipe.step`）。
- 与批量运行 `h_pipeline_run` 并存（批量入口保留，零回归）；两者输出契约不同
  （一次性 JSON vs SSE），逻辑重叠限于"装配 + 帧循环骨架"。

## 4. 前端设计（test.html）

- `<canvas id="video_canvas">` 绝对定位盖在 video 上，尺寸随视频显示尺寸；`requestAnimationFrame` 绘制。
- `EventSource` 收 `frame` → 存 `Map<n, result>` 与递增数组；`meta` → 取真实 `fps`（替换硬编码 25）
  与被分析视频的**原始宽高**（`width/height`，供叠加换算兜底）。
- 帧号映射：`n = floor(currentTime × fps)` → 二分取 ≤ n 的最近分析帧（抽帧时"框保持"到下一分析帧）。
- **坐标换算**：视频在元素框内按比例 contain（可能有黑边），故用统一缩放 `min(dw/原宽, dh/原高)`
  + 居中偏移；宽高优先用 `meta` 的原始分辨率（转码预览可能缩到 1920，`videoWidth` 已非原分辨率）。
- **陈旧度闸门**：视频时间跑过"已收到结果的最新时间"超过 0.2s（结束后继续播、拖进度条超出
  分析范围）即不画冻结的旧框，改在画面顶部提示「当前帧未分析（已超出分析范围）」。
- 播放节流：`currentTime ≥ lastResultTs` → `video.pause()` + HUD 显示「缓冲中…」；新结果到达且
  因缓冲暂停 → 续播。首次等 1~2 个结果再起播，避免立刻卡顿。
- `done` 时 `video.pause()` 停在最后一个分析帧，避免视频继续跑而框被冻结。
- 绘制：检测框按类别配色 + 置信度/类别；车牌框绿色 + 车牌号。
- 控件：「同步播放运行」/「停止」按钮；保留原「运行」（批量）按钮。

## 5. Range 支持（顺带修复）

`_send_file` 增加 `Range` 解析：`bytes=start-end` → `206 Partial Content` +
`Content-Range`/`Accept-Ranges`；无 Range → 200 全量。让播放器可拖动进度条（批量回看也受益）。

## 6. 已知约束（诚实说明）

- **播放速度 = 处理速度**：CPU 上 YOLO 40–280ms/帧，25fps 视频的真实时不可能；
  这是方案 B 的固有约束（要真·实时需 GPU / 降 imgsz / 加大 frame_skip）。
- 抽帧（frame_skip>1）时非分析帧沿用上一分析帧的框（"保持"而非"消失"）——这是框连续的
  实现方式，但也是**固有滞后**来源：框最多滞后 `frame_skip-1` 帧（警用链路 frame_skip=15
  约 0.5s），快目标会看到框落在身后；陈旧度闸门只解决"结束后/拖进度条"的冻结漂移，不解决
  该滞后（要更贴需调小 frame_skip 或做帧间插值）。
- 只叠加检测/车牌框与告警文本；VLM 素材图不回传（保持零带宽）。
- 前端叠加为 canvas 绘制，不做视频转码；浏览器需支持 EventSource（主流均支持）。

## 7. 验证方案

- SSE 冒烟：`curl -N '<stream url>'` → 依次出现 `meta` / 多条 `frame` / `done`。
- Range：`curl -r 0-99 -o /dev/null -w '%{http_code}' /files/videos/xxx.MP4` → `206`。
- 停止：运行中 `POST /stop` → 流在 ~1 帧内结束并回 `done`（processed 停在当前值）。
- 批量入口与既有测试零回归；前端页面可加载（叠加效果需人工目检）。

## 8. 解码适配（按需 H.264 转码）

**问题**：项目素材 7/8 为 **H.265/HEVC（4K）**，浏览器 `<video>` 基本不解（Chrome/Firefox
无硬解时黑屏），只有 H.264 素材能播——播放器本身没问题，是编码问题。

**方案**：服务端按需把非浏览器友好编码转成 **H.264/AAC MP4** 并缓存，源文件不动；
前端选视频时先问后端"能不能播"，不能播就显示转码进度、转完再播。

- `GET /api/video/prepare?name=`：ffprobe 探测编码 → 浏览器友好（H.264/yuv420p + 常见
  音轨）直接回 `{status:"ready", url:"/files/videos/<name>"}`；否则后台 ffmpeg 转码，
  回 `{status:"transcoding", progress, url:"/media/videos/<name>"}`，前端 1.5s 轮询。
- `GET /media/videos/<name>`：转码缓存文件的 Range 服务（转完才命中，否则 404）。
- 缓存键 `源名+大小+mtime+参数版本` 哈希 → `out/transcoded/<stem>.<hash>.mp4`（不入库，
  已 gitignore）；源变自动重转。转码参数：`libx264 -preset veryfast -crf 23 -pix_fmt
  yuv420p -c:a aac -movflags +faststart`，**宽 >1920 等比缩到 1920**（预览够用、体积/解码
  成本大降）。
- **坐标换算**：分析仍用原视频（bbox 为原分辨率），预览可能被缩到 1920，故叠加层改按
  `/api/video/info` 的**原始宽高**换算（`videoInfoCache.width`），不再用 `video.videoWidth`。
- 依赖 **ffmpeg/ffprobe**（本机已装）；缺失时 HEVC 源回错误提示，H.264 源不受影响。

**约束**：首次播放 HEVC 需等转码完成（4K 长片可能数分钟，进度条可见；之后走缓存秒开）；
转码与链路分析各自读原视频，互不影响。
