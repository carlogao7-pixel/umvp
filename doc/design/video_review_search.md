# 历史视频回顾检索（设计稿）

> 状态：📐 设计稿（未实施；2026-09-24 初稿，2026-09-29 并入 WeMM 向量链路与两级索引精定位，2026-10-16 随文档目录重整迁移）
> 需求：回顾历史视频时，用一句自然语言提问（如"哪段视频里有人群聚集""找把棚屋识别成车的那段"），
> 系统自动检索历史素材，返回相关**视频 + 时间位置**（精确到帧级），点击即跳转播放。
> 结论先行：**离线建片段索引 + 在线三级检索**，不重跑视频；索引分三档（轻/语义/向量），
> 语义与视觉向量由已部署的 **WeMM-Embedding** 服务承担（模型/服务/客户端对接见专篇
> [《WeMM嵌入对接》](wemm_integration.md)，本文只写业务流程与实现方案）；向量索引以独立链路
> **PIPE0004「视频向量化-嵌入查询」**落地。

## 1. 现状与缺口

- 链路运行结果（timeline 逐帧记录 / 检出 / VLM 研判 / 告警）只在本次响应里返回给前端，**跑完即失**，
  没有任何"内容索引"落库；数据库只有配置（presets / pipelines）。
- 关键帧/告警帧图片按 `output_dir` 落盘，但无索引，事后只能人肉翻目录。
- 可直接复用的既有能力：
  - **VLM 端点**（qwen3-vl-32b，OpenAI 兼容，`VLM0001` 配置）——可为任意帧生成文字描述；
  - **WeMM-Embedding 服务**（已部署在独立设备、待启动；OpenAI 兼容 `/v1/embeddings`）——
    文本/图片/视频片段统一向量空间，是③语义排序与"文搜视频"的引擎（对接专篇 §1–§3）；
  - **SSE 播放器**（[《实时播放叠加》](live_overlay.md)：Range 206 + 播放跳转 + canvas 叠加）——命中后跳转播放现成；
  - **FaceStore 向量底库先例**（numpy 线性检索，千级 <1ms）——向量检索形态可复制；
  - **链路机制**（帧管理抽帧 / YOLO 检出 / 事件尾逐条落盘）——索引构建就是"跑一遍链路并落产物"。

## 2. 总体思路：两阶段，检索永不重跑视频

```
入库（离线，每视频一次）：
  视频 → 回顾索引链路跑一遍（轻/语义档：检出统计 + 告警事件 + VLM 描述 + 缩略图）
       → 向量索引链路跑一遍（向量档：WeMM 片段/帧向量，PIPE0004）
       → 片段索引记录落库

查询（在线，秒级）：
  自然语言 → LLM 解析成检索意图
            → ① 结构化过滤（SQL）→ ② 关键词匹配 → ③ 语义向量排序（WeMM）
            → Top-K 片段列表（视频名 / 时间段 / 命中原因 / 摘要 / 缩略图）
            → 点击跳转播放（currentTime = 命中帧时间 − 回退量）
```

**三个关键取舍**（来自"逐帧向量 vs 整段单向量"的对比结论）：

1. **索引粒度 = 片段（如 5 秒/条），不是整段视频一个向量**——需求必须回答"什么时候发生"，
   片段粒度天然保住时间定位；短暂事件（1–2 帧的误检、瞬时动作）也不会被整段平均稀释。
2. **时序/场景语义靠 VLM 描述文本承载，与 WeMM 向量互补**——描述可解释、可人工校对、
   可直接全文检索；向量管召回（像不像），描述管解释（为什么），两层各司其职。
3. **语义向量直接上 WeMM（已部署），本机零 GPU**——原"轻量文本嵌入（bge/gte ONNX）"
   降为 WeMM 不可用时的备选降级位；向量模型的全部对接细节（serving/请求 schema/
   联调清单）收敛在[《WeMM嵌入对接》](wemm_integration.md)，本文不重复。

## 3. 索引层：两种索引链路 + 三档打标

### 3.1 形态

索引构建 = web_lab 新增「回顾索引」**运行模式**（与批量运行 / SSE 流式运行并列的
驱动层入口），把链路运行产物持久化。两种链路，可对同一视频先后各跑一遍
（同片段粒度，元数据合表 upsert）：

```
回顾索引链路（结构化 + 描述）：
  帧管理（稀疏抽帧，如 frame_skip=15）→ YOLO（全类别或指定类别）
    → 标注（可选，供缩略图带框）→ VLM 打标（语义档）
    → 输出处理（inspection：逐片段一条）→ 索引记录落库

向量索引链路 PIPE0004「视频向量化-嵌入查询」（独立保留链路，第四条）：
  帧管理 → 视频嵌入（片段聚帧：默认 5s 窗 × 6 帧 → 远端 WeMM 嵌入
    → clip 向量 + frame 向量 + 元数据/缩略图入库）
  （无 YOLO、无告警——入库即目的，与 PIPE0003"截取落盘即目的"同型；可先于①②单独上线）
```

- 不改任何**既有**管道模块——PIPE0004 是新增模块 `umvp/video_embed/`
  （`WEMMClient` / `EmbedStore` / `VideoEmbedStage`，客户端细节见专篇 §4），
  帧管理复用 `composer.FrameManager`（取帧节奏 + 背压照旧）。
- 模块 ID `video_embed`，preset 前缀 **VEMB**（`db.py _ID_PREFIXES` 登记）。

### 3.2 打标分档（成本可控的关键）

| 档 | 额外调用 | 索引内容 | 适用 |
|---|---|---|---|
| 轻档 | 0 | 仅 YOLO 检出统计（类别×数量峰值/均值×track 数）+ 告警事件 | 全库首扫、纯结构化检索 |
| 语义档 | VLM 1 次/片段（关键帧+prompt"描述画面发生了什么"） | 轻档全部 + 一句话描述 + 缩略图 | 需要自然语言检索的视频 |
| 向量档（PIPE0004） | WeMM 1 次批量请求/片段（clip 多图 + 逐帧单图合一发） | clip 向量（默认 1024 维）+ frame 向量（默认 256 维）+ 缩略图 | 文搜视频、相似检索、时间精定位 |

成本量级：30 分钟视频 ≈ 360 片段（5s/片）——轻档 = 纯 YOLO（yolov8n@640 CPU 39ms/分析帧，
GPU 12ms）；语义档 + 360 次 VLM（按片段节流，**不逐帧**）；向量档 + 360 次 WeMM 批量请求
（分钟级完成，成本明细见专篇 §5）。三档**可任意组合、分别补跑**（幂等 upsert）。

### 3.3 片段窗口与聚合

- 窗口可配（默认 5s）；窗口内聚合：
  - `det_stats`：各类别 `{max, avg, track 数}`（过滤链后的有效检出）；
  - `events`：命中的告警事件（警情类型 / 车牌号 / 人脸记录引用）；
  - `description`：VLM 描述（轻档为空）；
  - `thumb`：窗口首帧缩略图（落盘引用，非 base64 入库）；
  - 向量档附加：clip 向量入 `out/video_vecs.npz`；frame 向量 + 分析帧 ts 入
    `out/video_frame_vecs.npz`（两级索引第二层，见 §4.1）。
- **增量与幂等**：同视频重跑按 `(video, t_start)` upsert；视频文件不变则索引不重建；
  H.264 转码缓存（`out/transcoded/`）沿用，播放路径零改动。

## 4. 查询层：意图解析 + 三级漏斗

```
"上周哪段有人群聚集？"
   │  LLM 意图解析（同一 VLM 端点的文本调用，输出 JSON）
   ▼
{时间范围: 上周, 类别: 0(人), 数量阈值: >=4, 语义: "人群聚集", 关键词: []}
   │
   ├─ ① 结构化过滤（SQL）：时间范围 / 类别 / 数量 / 告警类型 / 车牌号
   ├─ ② 关键词匹配：description 全文（LIKE / FULLTEXT）
   ├─ ③ 语义向量（WeMM）：查询文本（或图片）→ WeMM 嵌入 → 与 clip 向量余弦排序
   ▼
融合排序 → Top-K：[{video, t_start, t_end, score, why, description, thumb}]
```

- **①② 阶段 1 即可用**：能回答"哪段人多 / 车流大 / 出现过车牌 X / 触发过交警类警情"。
- **③ 阶段 2（WeMM）**：回答"找像路边纠纷的画面"这类**无精确关键词**的语义问法；
  以图查片段同理（查询侧换单图输入，同一端点）。形态复制 FaceStore：npz 存向量、
  元数据存 MySQL、numpy 线性检索（万级片段 <10ms，无需向量库）。
- **why 字段**：每条命中标注召回来源（结构化命中 / 关键词 / 相似度分），空结果可解释，
  与 OutputPolicy"非法配置快速失败"同一可用性标准。

### 4.1 时间精定位：clip 粗排 + 帧级精排

只靠 clip 向量，命中只能定位到"某 5 秒窗口"（±1 窗口）。要定位到**具体画面在视频的
时间位置**，向量档入库双写一层帧级向量、查询分两步：

```
查询两步漏斗：
  查询向量 → ① × clip 矩阵 → Top-K 片段（K = top_k_clips，默认 10）
          → ② 仅在这 K 片段的 frame 向量内精排 → 最相似帧 → t = 该分析帧时间戳
          → 播放 currentTime = t − pre_roll_sec（默认 1s，避免从窗口头看起）
```

- **定位精度 = 分析帧间隔**（frame_skip=15、25fps ≈ 0.6s）；可选第三级：对 Top-1 片段
  查询时按 1fps 二次密集抽帧精排（在线补几次嵌入调用，换秒内精度）。
- 入库不加成本：clip 多图消息 + 逐帧单图消息**合并一次 HTTP 请求**批量发出
  （`/v1/embeddings` 的 input 数组，细节见专篇 §4.2）。
- **帧内空间定位（目标在画面哪里）不是向量的能力**：命中片段需要时可复用
  YOLO+标注模块重放出叠加框（既有模块，SSE 重放形态），与向量检索正交。

## 5. 存储设计

| 存储 | 内容 | 说明 |
|---|---|---|
| 新表 `review_index` | 片段元数据：video、t_start/t_end、det_stats JSON、events JSON、description TEXT、thumb_path、已建档位标记 | 业务 ID 照 `_ID_PREFIXES` 规则扩展（前缀 `RVIDX`）；索引 `(video_id, t_start)`；三档共用一张表（向量本体不入库，行上标记已建到哪档） |
| `out/video_vecs.npz` | clip 向量（ids + float32 矩阵） | 对齐 FaceStore 形态；30 分钟视频 360 片段 × 1024 维 ≈ 1.5MB |
| `out/video_frame_vecs.npz` | frame 向量（ids 挂所属 clip + 分析帧 ts + 矩阵） | 两级索引第二层（§4.1）；≈ 2900 帧 × 256 维 ≈ 3MB |
| `out/review_vecs.npz` | 描述文本向量（描述参与③排序时） | 同形态；备选轻量嵌入（降级位）也落此文件 |
| 无 DB 降级 | `--no-db` 时索引落 `out/review_index.json` | 小规模可用，检索逻辑同一套代码 |

向量维度/型号不一致的向量拒收并指明（维度约束见专篇 §2.2）；模型/维度变更按新版本
追加，检索按 `(model, dimension)` 过滤，新旧共存。

## 6. 前端交互

- web_lab 新增"回顾检索"页（或 test.html 新 tab）：输入框 + 结果卡片列表
  （缩略图/时间段/摘要/why）。
- 查询参数：`query_text`（或 `query_image`）、`top_k_clips`（粗排片段数，默认 10）、
  `top_k_frames`（精排返回帧数，默认 3）、`pre_roll_sec`（播放回退秒数，默认 1.0）、
  `video` / 时间范围过滤（可选）。端点/维度沿入库 preset，不重复配。
- 点击卡片 → 复用现有播放器：`video.currentTime = t_frame − pre_roll_sec`
  （Range 206 已支持拖动定位），可选带出该片段的检出框叠加（SSE 形态重放，数据已在索引里）。

## 7. 分级实施路线

| 阶段 | 引入 | 能回答的问题 | 成本 |
|---|---|---|---|
| 1 | 索引落库（轻/语义档）+ ①②检索 + 跳转播放 | "哪段人多/车多/出现过某车牌/触发过某类警情" | 零新模型，纯工程 |
| 2 | WeMM 接入：PIPE0004 向量档索引 + ③向量排序 + 两级索引精定位 | "找像 XX 的画面"（无关键词依赖、文搜视频、精确定位到帧） | 远端 WeMM 服务（已部署，对接见专篇）；本机零 GPU |
| 3（备选） | 轻量文本嵌入（bge/gte 系 ONNX，CPU） | 同③，WeMM 不可用时的降级 | 检索接口不变，换召回源 |

阶段 2 展开步骤：① 服务端按专篇 §3 启动 + curl 冒烟，回填专篇 §6 待确认清单 →
② `umvp/video_embed/` 三文件 + mock 单测（不依赖真端点）→ ③ `server.py` 注册模块/
参数/测试页、播种 PIPE0004（`_seed_pipeline()` 幂等追加）、`db.py` 登记 VEMB 前缀 →
④ 查询页 + 两级检索 + 精定位跳转 → ⑤ 真端点联调跑通 1 个真实视频 → ⑥ `DEPLOYMENT.md`
记台账（新增模块/新表/新链路，属影响部署改动）。阶段 1、2 无依赖冲突，可并行。

WeMM 向量做粗召回（"哪些片段相关"），结构化/描述索引做精排与解释（"具体何时、
为什么命中"）——两级索引架构，③ 对召回源透明（WeMM ↔ 轻量嵌入互换，契约不变）。

## 8. 边界与不做的事

- **不改既有管道模块**：帧管理/YOLO/VLM/输出处理零改动；PIPE0004 是**新增**模块
  不是改模块；索引构建是驱动层新运行模式。
- **检索不重跑视频**：查询只读索引；索引未覆盖的视频提示"未入库，可发起索引"
  （唯一例外：§4.1 可选第三级对 Top-1 片段的在线密集抽帧精排，量级几次调用）。
- **不替代告警链路**：回顾检索是事后能力，实时告警仍走既有 OutputPolicy 漏斗。
- **误检鲁棒**：语义命中以 VLM 描述 + 向量相似度为准（VLM 本身是误检语义兜底），
  YOLO 误检只影响 det_stats 权重，不误导语义检索。
- **向量模型对接细节不在本文**：serving 启动、请求 schema、截维约束、联调清单
  统一见[《WeMM嵌入对接》](wemm_integration.md)。

## 9. 验证方法（断言式）

1. 索引：对 1 个测试视频建索引 → 片段数 = ⌈时长/窗口⌉；重跑 upsert 幂等（行数不变）；
   `--no-db` 降级出 JSON 文件且可检索。
2. ①② 检索：构造已知内容视频 → "人群聚集"（结构化）命中 t_start 误差 ≤ 1 窗口；
   时间范围过滤生效；无命中返回空列表且 why 可解释。
3. ③ 向量检索（阶段 2）：对已知内容视频（如行人片段）以"行人"文本查询 →
   clip Top-1 命中该片段（t_start 误差 ≤ 1 窗口）；空库返回空 + 原因。
4. 精定位（两级索引）：对已知画面查询 → 返回 t = 该分析帧时间戳（误差 ≤ 1 帧间隔）
   且落在命中 clip 内；播放起点 = t − pre_roll_sec。
5. 降级：WeMM 端点不可达时报错信息含端点地址、快速失败；`use_real_embed=false`
   全流程可跑通；维度/型号不匹配的向量入库被拒并指明。
6. 跳转：返回的时间位置经播放器能定位播放（Range 206）。
7. 回归：`umvp/pipe/test_composer.py` 及既有链路测试全绿（本链路零侵入既有模块）。
