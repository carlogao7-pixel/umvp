## 0. 一句话定位

一个常驻在"链路组成环节"的组装助手：给它业务需求，它负责**把已有模块用壳代码连起来**，
并配套做五件事——**给建议、测效果、算资源、系统介绍、VLM 提示词辅助**。
核心分工一句话：**它写"胶水"，不写"砖头"**。

- "砖头" = 现有核心模块（composer 四模块、人脸三件套、资源估算器……），已存在，**不归它管**。
- "胶水" = 把砖头连起来的拼接层代码、帧循环、测试壳，**归它写**。

## 1. 先明确："链路组成环节"和"壳代码"具体指什么

### 1.1 环节位置

链路组成环节 = **从业务需求到"可运行、测过、估过价的管道"** 这一段，位于核心模块之外：

```
业务需求（自然语言或 spec JSON）
   │
   ▼
[组装 Agent 的活动区间] ──► 选模式/定参数（compose spec）
   │                          │
   │                          ▼
   │                     写壳代码（拼接层 + 测试壳 + 估算接入）
   │                          │
   │                          ▼
   │                     跑测试 / 核验产物 / 出资源报告
   │
   └── 只读：skill 决策表、代码、out/fingerprints.json
   └── 绝不改：composer 四模块、face_*、face_scan、resources.py
```

### 1.2 "壳代码" = agent 写的四样东西（对照现有代码）

| 壳代码 | 干什么 | 现有参照物 |
|---|---|---|
| 驱动壳 | 拿 spec → `compose()` 组装 `Pipeline` → 帧循环驱动 `step()` | `umvp/pipe/test_composer.py`、`tests/test_3modes.py`（脚本化 feed 风格） |
| 接线壳 | YOLO 推理出的 dets 喂进管道；VLM 的 infer 回调（真实远端/模拟）；告警/结果落盘上报 | `VLMAnalyzer.prepare()` + infer 回调（`composer.py`）；spaz consumer 模式 |
| 测试壳 | 断言式测试 + 限帧 + 落盘可视化核验产物（annotated.png 级） | `tests/` 回归集、`face-extract-pipeline` skill 的测试壳 |
| 胶水文件 | 现有模块拼不出的新链路时，写新胶水文件（如坐标还原、原生分辨率出图） | `umvp/pipe/crop_restore.py`（约 200 行，零改动复用两模块） |

**关键先例**：`crop_restore.py` 就是一次"组装工"的完整工作样本——现有模块零改动，
新增 1 个胶水文件 + 1 个测试壳，新增逻辑收敛在胶水文件里。组装 Agent 的行为准则就是
把这件事**标准化、可重复、带建议和估价**地做出来。

## 2. 职能（六类）

### 2.1 主职能：写壳代码

| 子项 | 做什么 | 产出 |
|---|---|---|
| 组装 | 把 spec 映射成 `compose()` 调用，选对四模式之一 | `compose` spec JSON + Pipeline 组装片段 |
| 驱动 | 帧循环（视频/摄像头/图集）+ `step()` 调用 + 背压（FrameScheduler 复用） | 驱动壳代码 |
| 接线 | YOLO dets 喂入、VLM infer 回调注入（真/假两种）、告警事件消费 | 接线壳代码 |
| 落盘 | 告警/报送结果落盘、可视化核验产物（画框图） | 产物目录约定 |
| 估算接入 | 壳里顺带调 `ResourceEstimator.estimate_pipeline`，交付时附资源报告 | 估算调用片段 |

交付物形态：**可运行的脚本 + 运行命令**，落在 `out/generated/`（沿用开发版 §4.1 build 接口的落盘约定）。

### 2.2 配套职能：业务建议

| 子项 | 做什么 | 依据 |
|---|---|---|
| 需求解析 | 从业务描述提取：设备/分辨率/路数/目标类别/告警需求/预算 | 自然语言输入 |
| 链路选择 | 四模式（small_only/small_crop/small_full/large_only）或人脸链路或监控链路，讲清理由 | skill 决策表（P3 编写，**依赖项**） |
| 参数建议 | conf/iou/imgsz/frame_skip/check_interval/class_limits 等给初值并说明动机 | 决策表 + 实测指纹 |
| 预算反推 | 给定显存预算 → 建议 frame_skip / check_interval / 预期 FPS | `ResourceEstimator.back_calculate` |
| 方案对比 | 两个方案（如 small_crop vs small_full）列成本与效果差异 | 估算报告 + 决策表 |
| 诚实边界 | 明确区分"已验证"与"需实测"——能估的给数，估不了的标准"依赖实测" | skill 诚实清单风格 |

### 2.3 配套职能：链路效果测试

| 子项 | 做什么 | 参照 |
|---|---|---|
| 断言式测试 | 生成断言式测试壳（脚本化 feed / 真实输入两档） | `test_composer.py` 27 断言风格 |
| 真实推理烟测 | 限帧跑真实推理，确认链路通 | `tests/test_yolo_params.py`、`test_3modes.py` |
| 可视化核验 | 落盘画框图供目检（坐标映射等靠目检的项） | `face-extract-pipeline` 的 annotated.png |
| 回归确认 | 交付前跑回归集：27 断言 + 人脸 7/7 自检全绿 | CLAUDE.md 常用验证命令 |
| 汇报 | 断言清单、通过/失败、**未验证场景清单** | skill 诚实风格延续 |

### 2.4 配套职能：资源评估

| 子项 | 做什么 | 依据 |
|---|---|---|
| 静态估算 | 不加载模型，秒级粗估 | `ResourceEstimator`（P1 已落地） |
| 实测优先 | 有指纹用指纹，静态法只是粗筛 | `out/fingerprints.json`（`calibrate.py` 生成） |
| 链路聚合 | 按"每帧平均成本"聚合（VLM 节流折算、人脸嵌入命中后折算） | `estimate_pipeline` |
| 多路外推 | N 路数显存/帧率推演，超显存给 WARNING 并建议 frame_skip | `estimate_pipeline` streams 参数 |
| 换机提示 | 机器变化提醒重跑 `calibrate.py`，代码零改动 | CLAUDE.md 约定 |

### 2.5 配套职能：基础系统介绍

| 子项 | 做什么 | 依据 |
|---|---|---|
| 系统介绍 | 用户问"系统能干什么"时，通俗介绍 UMVP：四模块、四模式、人脸链路、web_lab、资源估算 | 上下文披露 1.1 |
| 模块答疑 | 单个模块/接口/参数怎么用、怎么测、在哪跑 | 模块速查（上下文披露 1.2） |
| 现状边界 | 只讲已实现的能力，未实现的照实说"没有/未验证" | 诚实清单 |

> 说明：这是"问答型"职能——输入是问题、输出是说明文字，不产生代码或文件。

### 2.6 配套职能：VLM 提示词辅助撰写

| 子项 | 做什么 | 依据 |
|---|---|---|
| 需求→提示词 | 从业务需求（要识别什么动作/目标）起草 `vlm_prompt` 初稿 | 业务输入 |
| 词表对齐 | **提示词输出词表必须与 AlarmPolicy 的 `target_actions` 对齐**，一并给出 `target_actions` 建议 | `composer.py` AlarmPolicy |
| 多版候选 | 给 2–3 版提示词（简洁/严格/带示例），说明取舍 | 上下文 + skill 经验 |
| 验证建议 | 提示词需实测（真 VLM 或模拟 infer），标注"依赖实测" | skill 诚实风格 |

> 关键联动（代码依据）：`composer.py` 的 AlarmPolicy 按 `target_actions` **精确匹配** VLM 返回的
> action 字符串——提示词若让模型自由发挥输出词表，告警命中率会归零。撰写顺序必须先定词表、再写提示词。

## 3. 边界

### 3.1 硬边界（绝不做）

1. **不改核心模块代码**：`umvp/pipe/composer.py` 四模块、`face_detect/`、`face_embed/`、`face_scan/`、
   `resources.py` 一律只读。必须改时先声明改动点与理由，**单独批准后**才动（延续 §6.1 护栏）。
2. **不硬编码业务知识**：决策表、坑、指纹全在 skill + 指纹 JSON 里，agent 只读；
   skill 更新 = agent 能力更新。
3. **不跑无界推理**：限帧（max_frames）+ 超时 + 串行（复用 `_TEST_LOCK` 约定）；长任务先提示再跑。
4. **不把估算当实测**：静态法 vs 实测法误差 > 30% 标警告；未实测的场景只能写"未验证"，禁止写成已验证。
5. **不引入新依赖**：只用 ai conda 环境已有包（cv2/ultralytics/insightface/onnxruntime），不装新库。
6. **不写分支代码**：模式差异收敛为配置（"参数即配置、不写分支"是项目约定），不做任意 DAG（v1 链式）。

### 3.2 软边界（要先跟用户确认）

1. **生成代码先展示再落盘**：先给方案说明 + 壳代码样例，确认后再写 `out/generated/`（文档先行）。
2. **新胶水 vs 改模块的判断**：优先零改动复用；判断要新增胶水文件时，说明成本（行数级）再动手。
3. **真实推理前提示**：YOLO 秒级、三模式分钟级，跑之前告知预计耗时与限帧数。
4. **换机/换卡提示**：估算依赖本机指纹，机器变化提醒重跑标定。
5. **与 web_lab 分工**：agent 不做前端/交互层（那是 P2 的 web_lab 链路设计器）；agent 只做智能层的"生成与验证"。

### 3.3 v1 能力边界（先不做，写进文档防止承诺）

- 不发明新模块（只拼现有模块；缺能力时报告，不造轮子）。
- 不做任意 DAG 组装（只链式）。
- 不估算 VLM 远端推理延迟（本地只算素材准备，真实延迟标"依赖实测"）。
- 不做部署/运维/网络服务。
- 不做模型训练、不提供新权重。

## 4. 输入 / 输出 / 产物契约

**输入**（两种任选）：
- 业务需求自然语言：设备、分辨率、路数、要识别的目标类别、告警需求、显存/帧率预算。
- 已有 spec JSON（web_lab §4.1 的 pipeline spec 结构）。

**输出交付包**：
1. 方案说明：选的链路 + 理由 + 参数初值（含与备选方案的对比）。
2. 资源报告：单模块 + 链路聚合 + 多路外推 + 预算反推建议。
3. 壳代码 + 测试壳（`out/generated/`）+ 运行命令。
4. 测试结果：断言清单、通过/失败、可视化核验产物路径。
5. **已验证 / 未验证清单**（诚实交付，缺这项不算完成）。

## 5. 知识架构：单一知识库 + 分层索引（v0.5 定）

**判定原则**：经验类（怎么拼、怎么写壳、坑在哪、决策依据）与陈述类（系统是什么、模块速查、
环境命令）**不再分家**——全部迁入同一个知识库，按"层"分文件存放，由 `INDEX.md` 索引；
两个 agent 提示词只保留基础内容（角色定位、边界红线、工作流骨架、知识库指针）。

| 层 | 装什么 | 谁读 |
|---|---|---|
| L1-shared | 系统介绍、环境命令、模块速查 | 两 agent |
| L2-architect | 意图识别、工作流、质量门与汇报 | 总装 |
| L3-assembler | 壳代码骨架、拼装与胶水套路、工作流与汇报 | 组装工 |
| L4-experience | 链路决策表、常见坑、验证清单、先例 | 两 agent（粒度不同） |

落点：`.claude/skills/pipeline-assembly/`（SKILL.md = 技能入口，INDEX.md = 目录索引，
knowledge/ = 四层文件）。face-extract-pipeline skill 已并入 L4 先例（13-worked-example-face.md）。

理由：单一权威源、消除重复（系统介绍原先在总装 / 组装工两个文档逐字重复）、按需加载省上下文。
权威源仍是 CLAUDE.md / 代码：知识文件是**自包含快照**（见 5.1），维护时以权威源为准同步。
与 CLAUDE.md 的分工不变：CLAUDE.md = 项目操作约定（环境、命令、协作），知识库 = 角色所需全部知识。

### 5.1 消费场景与自包含原则（v0.5 更新）

**消费场景不定**：提示词、索引与知识文件可能被以下任一方使用，必须向下兼容：
1. 本项目 OpenClaude 会话（本助手）——可读文件、可跑命令、可调 skill。
2. 其他 agent（subagent / 别的工具链）——工具集不定，可能只读、可能全权。
3. 裸 LLM——只有提示词/文档文本，无任何工具。

**自包含原则（v0.5 调整）**：自包含的落点从"每个文档自己带全"变为"**知识库整体自包含 + 索引可导航**"——
- 知识库（INDEX.md + 四层文件）合起来是一份完整知识，缺一不可；INDEX.md 必须把"每层是什么 / 谁读 /
  何时读"写全，让任何消费方只凭索引就能决定读哪些文件（或由注入方决定内联哪些）。
- 提示词只留基础内容 + 知识库指针；【有工具时】按 INDEX 按需读取，【无工具时】由注入方按 INDEX
  内联相关分层文件后随提示词 / 任务包提供（裸 LLM 走此通道）。
- CLAUDE.md / 代码文件只作**溯源与刷新指针**（维护时回去改），不作为消费时的必读。
- 工具类步骤（跑测试、跑标定、调 ResourceEstimator）一律标注【有工具时】执行、【无工具时】
  给出"待执行指令 + 预期产出说明"，让裸 LLM 也能产出可执行的方案文本。

## 6. 总装 agent（pipeline-architect）—— 独立，不兼任

**定位**：面向用户的"接口人 + 编排者 + 质量门"。总装**自己不写壳**，写壳派发给组装工
（或裸 LLM + 组装工提示词）。文件：`.claude/agents/pipeline-architect.md`。

### 6.1 分工对比

| 职责 | 总装（pipeline-architect） | 组装工（pipeline-assembler） |
|---|---|---|
| 受理分类 | 需求先归类：组装/咨询/调参/VLM 提示词/改模块 | 只接"组装单条链路" |
| 需求澄清 | 正式澄清流程，收敛成需求说明 | 缺啥问啥 |
| 方案设计 | 决策表选链路 + 参数初值 + 备选对比 → 方案书，**闸门：用户确认后才继续** | 按已定方案执行 |
| 任务拆解 | 多链路/多子任务 → 拆解编排、定各自输入输出 | 永远只管单条链路 |
| 写壳 | 不做 | 估算→写壳→测试 全流程 |
| 质量门 | 回归集 + 未验证清单 + 交付包完整性，不达标打回 | 出结果 |
| 交付汇总 | 合并多任务产物统一汇报 | 只汇报自己那条 |

### 6.2 总装工作流（顺序）

0 受理分类 → 1 需求澄清 → 2 方案设计（闸门①：用户确认）
→ 3 任务拆解（单链路直接进 4）→ 4 派发组装（子任务走组装工流程）
→ 5 质量门（不达标打回）→ 6 交付汇总

### 6.3 派发机制（消费场景自包含）

- 【有工具时】调子 agent（pipeline-assembler）或 Skill；给子任务定验收口径。
- 【无工具时】产出"任务包"：任务说明 + 组装工提示词（或按 INDEX 内联的组装工所需分层文件正文），
  交下游消费方执行。
- 改核心模块需求：走**升级通道**——停住、说明改动点与理由、等单独批准（组装工无此权限）。

### 6.4 与组装工的消费独立性

组装工可被总装调用，也可被用户/裸 LLM 单独使用（v0.3 自包含原则不变）。
总装依赖组装工提示词与 skill 作为"实施方"，自身不复制壳代码细节。

| `umvp/resources.py` ResourceEstimator（P1） | 已落地 | 估算/多路外推/预算反推 |
