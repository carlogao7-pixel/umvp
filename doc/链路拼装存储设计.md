# UMVP 链路拼装存储设计（pipelines + pipeline_steps）

> 技术设计文档。链路拼装（pipeline assembly）的持久化方案：用"模块配置引用 + 顺序"组织一条
> 可运行的视觉分析链路，取代"整份快照"式存储。与 P2 链路定制（`doc/需求文档-开发版.md` §4）
> 的 stage 式 pipeline spec 对齐。

## 1. 背景与目标

- web_lab 已支持把模块参数以 `kind='module'` 存入 `presets` 表，每份配置有自增 `id`
  （前端"保存"按钮 → `/api/presets/save`，见 `index.html` / `web_lab/db.py`）。
- 目标：新增"链路拼装信息"的存储。一条链路 = 一组**有序**的模块步骤，每个步骤**引用**一个
  已入库的模块 preset。
- 核心问题：**"拼装表只记模块参数在库中的 id 以及顺序，对吗？"**

**结论：基本对，但要补三块（见 §2.2）。** 用引用替代整份快照是正确方向——模块参数存一份、
多链路复用，改一处全体生效；但"id + 顺序"单独不够表达一条完整链路。

## 2. 设计决策

### 2.1 用"引用"替代"整份快照"

现状：`presets.kind='pipeline'` 把整条链路 spec 快照进 `params_json`
（`web_lab/server.py` 1049 行，前端"保存链路"按钮 → `index.html`）。缺点：

- 重复存储：模块参数在 `kind='module'` 与 `kind='pipeline'` 各存一份；
- 不同步：改模块参数后，已存的链路快照不会更新。

新方案：链路步骤只存 `presets.id` 引用。模块 preset 是"命名即身份、同名覆盖"
（`db.py` 116-118 行 UPDATE 同 id，覆盖后 id 不变），因此**覆盖模块 preset = 所有引用它的链路
同步生效**，无需逐链路改。

### 2.2 "id + 顺序"够不够？——三块补充

1. **链路级字段（缺）**：`streams`（多路外推）、`budget`（显存预算，P2 spec 里是
   `{"vram_mb": 8192}`）、场景描述等**不属于任何单个模块 preset**，是链路自身的配置。
   → `pipelines` 表独立列 / JSON 存。
2. **角色不用另存（从 preset 反查）**：步骤只存 `preset_id`，"这一步是哪个模块"
   （`frame_manager` / `yolo` / `vlm` / `alarm` / 人脸链路各环节）从 `presets.module_id`
   反查即可——`server.py` 1047 行已保证该值 ∈ `MODULES`。顺序 = 步骤在子表的 `position`。
   → 回答"要不要存 role"：**不用**，`module_id` 就是角色。
3. **引用完整性（缺）**：直接删除被链路引用的模块 preset 会让链路悬空。
   → 策略：`delete_preset` 先查引用、命中则**拒绝并报错（带链路名）**；DB 层加
   `FOREIGN KEY ... ON DELETE RESTRICT` 兜底（防绕过代码直接 SQL 删除）。

### 2.3 为什么用子表而非 JSON 列

- MySQL 表本身无序 → 顺序需要显式 `position` 列，不能依赖插入序；
- 子表可加外键、可直接回答"哪些链路引用了这个 preset"（引用检查、列表反查）；
- 覆盖链路 = 删 steps 重建（事务保证 `pipelines` + `pipeline_steps` 原子）。

### 2.4 与 P2 pipeline spec 的关系

P2 设计（`doc/需求文档-开发版.md` §4.1）的 spec 是 `{name, stages:[{module, params}], streams, budget}`。
本方案正是它的持久化：

```
stages  ⇄  pipeline_steps（position 排序）+ presets（module_id + params_json）
streams / budget  ⇄  pipelines 独立列
```

## 3. 表结构（DDL）

```sql
CREATE TABLE IF NOT EXISTS pipelines (
  id INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(64) NOT NULL,
  streams INT NOT NULL DEFAULT 1,
  budget_json TEXT NOT NULL,      -- 显存预算等链路级参数，JSON（空 = {}）
  meta_json TEXT NOT NULL,        -- 链路级扩展字段（场景描述等），JSON（空 = {}）
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS pipeline_steps (
  id INT AUTO_INCREMENT PRIMARY KEY,
  pipeline_id INT NOT NULL,
  position INT NOT NULL,          -- 0..n-1，显式顺序（同链路内唯一）
  preset_id INT NOT NULL,         -- 引用 presets.id（须为 kind='module'）
  UNIQUE KEY uk_pipeline_position (pipeline_id, position),
  KEY idx_preset (preset_id),
  CONSTRAINT fk_step_pipeline FOREIGN KEY (pipeline_id) REFERENCES pipelines(id) ON DELETE CASCADE,
  CONSTRAINT fk_step_preset FOREIGN KEY (preset_id) REFERENCES presets(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

要点：

- `pipelines.name` 唯一 = "命名即身份"，同名保存 = 覆盖（与 `presets` 语义一致）。
- `pipeline_steps` 外键：删链路 → steps 级联删；删被引用的 preset → RESTRICT 拦住。
- `budget_json` / `meta_json` 存链路级参数；步骤参数**不**在这里，只存在于所引用的 preset。

## 4. 访问层（web_lab/db.py 新增）

| 函数 | 职责 |
|---|---|
| `list_pipelines()` | 列出全部链路（含每步 `{position, preset_id, module_id}`），按 `updated_at DESC` |
| `save_pipeline(name, preset_ids, streams=1, budget=None, meta=None)` | 新建/同名覆盖；校验步骤非空、preset 存在且为 `kind='module'`；事务内重建 steps，返回 `(id, 是否新建)` |
| `load_pipeline(pipeline_id)` | 按 id 取回完整链路：`{id, name, streams, budget, meta, stages:[{position, preset_id, module_id, params}]}`，不存在抛 `ValueError` |
| `delete_pipeline(pipeline_id)` | 删除链路（steps 级联/显式删），幂等 |
| `delete_preset(...)`（改动） | 先查 `pipeline_steps` 引用，命中则抛 `ValueError`（含引用的链路名），否则照旧删除 |

事务语义：`save_pipeline` 用 `conn.begin()/commit()/rollback()`，保证"插链路 + 重建 steps"
原子（当前连接 `autocommit=True`，需显式开事务，见 `db.py` 41-51 行连接配置）。

## 5. HTTP API（web_lab/server.py 新增）

沿用 `_preset_*` 的容错模式（DB 不可用 / 未启用时返回 `{ok:false, error}`，不影响服务器运行）：

| 接口 | 方法 | 请求体 | 说明 |
|---|---|---|---|
| `/api/pipelines` | GET | — | 链路列表（含每步 module_id） |
| `/api/pipelines/save` | POST | `{name, steps:[preset_id,...], streams?, budget?, meta?}` | 保存/覆盖；`steps` 数组顺序即 `position` |
| `/api/pipelines/load` | POST | `{id}` | 取回完整链路（stages 带 params） |
| `/api/pipelines/delete` | POST | `{id}` | 删除链路 |

## 6. 还原逻辑（链路 → 可执行 spec）

`load_pipeline` 已把 `stages` 拼成 `[{module_id, params}]`，可直接生成 P2 的 pipeline spec：

```
{name, streams, budget, stages: [{module: 步骤.module_id, params: 步骤.params}, ...]}
```

注意一个**边界**：stage 参数名与 `compose()` 扁平 spec 键名**不一致**——模块 preset 里 YOLO 参数叫
`conf/iou/imgsz`（`server.py` PARAMS["yolo"]），compose spec 里叫 `yolo_conf/yolo_iou/yolo_imgsz`
（`server.py` 408-411 行映射）。这个"参数名映射"属于 P2 `/api/pipeline/build` 的职责，
**不在 DB 层**——DB 只保证 stage 引用完整、参数原样可取。

## 7. 与现有 `kind='pipeline'` 快照的关系

- 保留 `presets.kind='pipeline'`：前端"链路暂存"栏（`index.html` 154-160 行）还在用，属 P2 stub 阶段存量。
- 两种机制并存：**快照式**（整机配置整体存取）与**引用式**（模块配置复用拼装）。P2 链路设计器
  落地后统一走新表，`kind='pipeline'` 可弃用。
- 迁移负担为零：当前 `presets` 无 `pipeline` 数据（`doc/数据库结构.md` §3.4 行数 0）。

## 8. 边界与后续

- v1 步骤只能是"已入库的模块 preset"；"自由步骤（参数未入库）"可先保存再引用，或后续给
  `pipeline_steps` 加 `params_json` 支持内联覆盖。
- `delete_preset` 被引用时拒绝删除——前端"删除配置"按钮会收到明确报错，属预期行为。
- 四模式 shortcut（`h_compose`）与 stage-based 设计器是两种入口，P2 统一到设计器。

## 9. 验证方法（断言式回归）

启动自含 MySQL（`doc/数据库结构.md` §2.1）后跑以下回归，全部通过即算验证闭环：

1. `init_db()` 幂等建表（重复调用不报错）。
2. 存两个模块 preset（如 `yolo` / `vlm`）→ `save_pipeline` 引用 → `load_pipeline` 断言
   stages 顺序、`module_id`、params 与保存一致。
3. 同名再次 `save_pipeline`（不同 steps）→ 返回同一 id，steps 被重建。
4. `delete_preset`（被引用的那个）→ 抛 `ValueError` 且报错含链路名。
5. `delete_pipeline` → steps 级联删；此时再 `delete_preset` 成功。
6. `list_pipelines` 按最近更新倒序。
7. 清理测试数据，库回到干净状态。
