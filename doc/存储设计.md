# 数据库存储设计（决策记录）

> 技术设计文档。记录 web_lab 命名配置暂存（presets）生态的两块存储设计的**来龙去脉与决策理由**；
> **当前结构**以 `doc/数据库结构.md` 为准（本文只记设计决策，不重复结构事实）。
> 本文由原《配置参数列式化存储设计》与《链路拼装存储设计》合并而成。

---

## 第一部分 配置参数列式化存储（每模块一张参数表）

### 1. 背景与目标

原设计（`doc/数据库结构.md` §3 的旧版）：所有模块的命名配置统一存 `presets` 一张表，参数整体
JSON 序列化进 `params_json`。问题：

- 可视化页想把参数展示成二维表时，不同模块字段各不相同，宽表（一个模块一行、所有模块字段当列）
  会随着模块数量**无限积累列**，且大量单元格为空；
- 参数以字符串 JSON 存储，无法按列类型约束/查询。

**方案（用户选定）：每个模块各自维护一张参数表**，参数展开为类型化列；`presets` 表降级为
"注册表"（只保留归属信息），`pipeline` 类型配置不受影响（仍是整份 JSON 快照）。

### 2. 设计决策

**presets 保留为注册表，不删**：仍承担 `id`（被 `pipeline_steps` 外键引用）、`kind`、`name`
（命名即身份，同名覆盖）、`module_id`、`created_at/updated_at`（列表倒序）。`kind='module'` 行的
`params_json` **迁移后置空**；`kind='pipeline'` 行不变，仍整体存 JSON（链路 spec 结构不固定，
不适合列式）。

**每模块一张参数表**：表名 `preset_params_<module_id>`（如 `preset_params_yolo`）。要点：

- 主键 = `preset_id`（一列一行，配置与参数 1:1）；外键级联删除——删注册表行时参数自动清理。
- 模块参数清单来自 `web_lab/server.py` 的 `PARAMS`（前端表单的"参数即表单"来源），
  **参数定义仍只有这一处**，DB 列只是它的物化。
- 表与列名均来自 MODULES 白名单（`[a-z0-9_]{1,32}`），防注入。

**类型映射（server.py 参数类型 → 列类型）**：

| 参数 type | 列类型 | 说明 |
|---|---|---|
| int | `INT` | 数值输入 |
| float | `DOUBLE` | 阈值、比例等 |
| bool | `TINYINT(1)` | 复选框，存 0/1 |
| select | `VARCHAR(64)` | 下拉选项（值短） |
| file | `VARCHAR(255)` | 文件/路径选择 |
| str | `VARCHAR(255)` | 短文本 |
| text | `TEXT` | 脚本、时间线、提示词等长文本 |

**列变更（模块日后加参数）**：加参数 → `init_db()` 对每个已注册模块校验表/列存在性
（`SHOW COLUMNS`），缺列时 `ALTER TABLE ... ADD COLUMN` 自动补列——**改 schema 不用手工 DDL**；
参数下线/标记 test_only 后其历史列自动删除（`_prune_stale_columns`，列随 schema 双向收敛）。

**读写路径**：save = 事务内 upsert `presets`（params_json=''）+ upsert `preset_params_<mid>`
（参数按类型强转）；load/list = 注册表行 + 模块参数表行组装 `{param: 值}`；delete = 删注册表行，
参数表级联删。`load_pipeline`（链路还原）的 stages 参数同样从模块参数表取回。

**旧数据迁移**：`init_db()` 里做一次幂等迁移：`kind='module'` 且 `params_json` 非空的行 →
按 `module_id` 拆列写入对应参数表 → 清空 `params_json`。已清空的跳过（幂等）。

**与可视化页的关系**：`GET /api/db/tables` 返回各表快照（二维数组 `columns` + `rows`），
前端"数据浏览"tab 渲染（presets 注册表、每模块一张参数表、pipelines/steps）。只读展示，
不做在线编辑/删除（改数据走现有"命名暂存"界面，保留引用完整性保护）。

### 3. 访问层（web_lab/db.py）

| 函数 | 变更 |
|---|---|
| `configure_modules(schemas)` | **新增**：server.py 启动时注册 `{module_id: {参数名: 参数type}}`，db 据此建表/强转 |
| `init_db()` | 建三张主表后，对每个已注册模块 ensure 参数表（含补列），再跑幂等迁移 |
| `save_preset(...)` | module 分支改事务拆列写；pipeline 分支不变 |
| `load_preset(...)` / `list_presets(...)` | module 分支改从参数表组装；pipeline 不变 |
| `load_pipeline(...)` | stages 参数改从模块参数表取回 |
| `delete_preset(...)` | 不变（参数表靠级联清理） |
| `table_snapshots()` | **新增**：返回各表 `{columns, rows}` 快照 |

## 第二部分 链路拼装存储（pipelines + pipeline_steps）

### 4. 背景与目标

web_lab 已支持把模块参数以 `kind='module'` 存入 `presets` 表。目标：新增"链路拼装信息"的存储。
一条链路 = 一组**有序**的模块步骤，每个步骤**引用**一个已入库的模块 preset。

核心问题：**"拼装表只记模块参数在库中的 id 以及顺序，对吗？"**
**结论：基本对，但要补三块**。用引用替代整份快照是正确方向——模块参数存一份、多链路复用、
改一处全体生效；但"id + 顺序"单独不够表达一条完整链路。

### 5. 设计决策

**用"引用"替代"整份快照"**：原 `presets.kind='pipeline'` 把整条链路 spec 快照进 `params_json`，
缺点是重复存储（模块参数两份）、不同步（改模块参数后旧快照不更新）。新方案链路步骤只存
`presets.id` 引用——模块 preset 是"命名即身份、同名覆盖"，因此覆盖模块 preset = 所有引用它的
链路同步生效。

**"id + 顺序"够不够？——三块补充**：

1. **链路级字段（缺）**：`streams`（多路外推）、`budget`（显存预算，如 `{"vram_mb": 8192}`）、
   场景描述等**不属于任何单个模块 preset** → `pipelines` 表独立列 / JSON 存。
2. **角色不用另存（从 preset 反查）**：步骤只存 `preset_id`，"这一步是哪个模块"从
   `presets.module_id` 反查即可；顺序 = 步骤在子表的 `position`。
3. **引用完整性（缺）**：直接删除被链路引用的模块 preset 会让链路悬空 → `delete_preset`
   先查引用、命中则**拒绝并报错（带链路名）**；DB 层加 `FOREIGN KEY ... ON DELETE RESTRICT` 兜底。

**为什么用子表而非 JSON 列**：MySQL 表本身无序 → 顺序需要显式 `position` 列；子表可加外键、
可直接回答"哪些链路引用了这个 preset"；覆盖链路 = 删 steps 重建（事务保证原子）。

**与链路 spec 的关系**：`{name, stages:[{module, params}], streams, budget}` 正是本方案的持久化——
`stages ⇄ pipeline_steps（position 排序）+ presets`；`streams / budget ⇄ pipelines 独立列`。

### 6. 访问层与接口

| 函数 | 职责 |
|---|---|
| `list_pipelines()` | 列出全部链路（含每步 `{position, preset_id, module_id}`），按 `updated_at DESC` |
| `save_pipeline(name, preset_ids, streams=1, budget=None, meta=None)` | 新建/同名覆盖；校验步骤非空、preset 存在且为 `kind='module'`；事务内重建 steps，返回 `(id, 是否新建)` |
| `load_pipeline(pipeline_id)` | 按 id 取回完整链路：`{id, name, streams, budget, meta, stages:[...]}` |
| `delete_pipeline(pipeline_id)` | 删除链路（steps 级联/显式删），幂等 |
| `delete_preset(...)`（改动） | 先查 `pipeline_steps` 引用，命中则抛 `ValueError`（含链路名） |

HTTP 接口：`/api/pipelines` GET、`/api/pipelines/save|load|delete` POST，沿用 DB 不可用时
返回 `{ok:false}` 的容错模式。

**边界**：stage 参数名与 `compose()` 扁平 spec 键名**不一致**（模块 preset 里叫 `conf/iou/imgsz`，
compose spec 里叫 `yolo_conf/yolo_iou/yolo_imgsz`）。这个"参数名映射"属于链路装配的职责，
**不在 DB 层**——DB 只保证 stage 引用完整、参数原样可取。

### 7. 与 `kind='pipeline'` 快照的关系

- 保留 `presets.kind='pipeline'`：为历史兼容保留（2026-09-20 起已完成链路统一走
  `pipelines`/`pipeline_steps` 引用式，`presets` 中已无 `kind='pipeline'` 行）。
- 两种机制并存：**快照式**（历史 JSON 快照，已停用）与**引用式**（`pipelines`/`pipeline_steps`
  的步骤引用模块 preset，现役）。当前三条保留链路（PIPE0001/0002/0003）均走引用式。

## 附：验证方法（断言式回归）

启动自含 MySQL（`doc/数据库结构.md` §2.1）后跑回归，全部通过即算验证闭环：

1. `configure_modules` 后 `init_db()` 幂等：重复调用不报错；各模块参数表存在。
2. module preset save → load：参数按类型往返一致（int/float/bool/str/text 各验证）。
3. 同名再次 save（不同参数）→ 同一 id，参数被覆盖。
4. 列表按 `updated_at DESC` 倒序；params 与库中一致。
5. 未注册模块的 module 行 load → `params={}`（容错）。
6. 存两个模块 preset → `save_pipeline` 引用 → `load_pipeline` 断言 stages 顺序、module_id、params 一致。
7. 同名再次 `save_pipeline`（不同 steps）→ 返回同一 id，steps 被重建。
8. `delete_preset`（被引用的那个）→ 抛 `ValueError` 且报错含链路名；删链路后再删成功。
9. pipeline 类型 save/load 不受影响（仍 JSON）；删除 module preset → 参数表行级联删除。
10. 旧 JSON 数据迁移：params_json 置空、参数落入对应模块表。
11. `table_snapshots()` 返回各表列/行与库中一致；清理测试数据，库回到干净状态。
