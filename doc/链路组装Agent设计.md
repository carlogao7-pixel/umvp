> 定位：P4 pipeline agent 的设计文档，回答两个问题——
> ① **能做什么、不能做什么**（职能与边界）；② **一个需求进来，从受理到交付一步步怎么走**（详细流程）。

## 第一部分 职能与边界

### 1. 一句话定位

两个 agent 分工协作：

- **总装（pipeline-architect）**：面向用户的"接口人 + 编排者 + 质量门"。自己**不写壳**，
  写壳派发给组装工。文件：`.claude/agents/pipeline-architect.md`。
- **组装工（pipeline-assembler）**：常驻在"链路组成环节"的组装助手，给它业务需求，
  它负责**把已有模块用壳代码连起来**，并配套做五件事——**给建议、测效果、算资源、
  系统介绍、VLM 提示词辅助**。只接"组装单条链路"。文件：`.claude/agents/pipeline-assembler.md`。

核心分工一句话：**它写"胶水"，不写"砖头"**。

- "砖头" = 现有核心模块（composer 四模块、人脸三件套、资源估算器……），已存在，**不归它管**。
- "胶水" = 把砖头连起来的拼接层代码、帧循环、测试壳，**归组装工写**。

### 2. 环节位置与"壳代码"

链路组成环节 = **从业务需求到"可运行、测过、估过价的管道"**，位于核心模块之外：

```
业务需求（自然语言或 spec JSON）
   │
   ▼
[组装工的活动区间] ──► 选模式/定参数（compose spec / 链路 stages）
   │                     │
   │                     ▼
   │                写壳代码（拼接层 + 测试壳 + 估算接入）
   │                     │
   │                     ▼
   │                跑测试 / 核验产物 / 出资源报告
   │
   └── 只读：skill 决策表、代码、out/fingerprints.json
   └── 绝不改：composer 四模块、face_*、face_scan、resources.py
```

**"壳代码" = 组装工写的四样东西**：

| 壳代码 | 干什么 | 现有参照物 |
|---|---|---|
| 驱动壳 | 拿 stages（模块+参数）→ `_chain_from_spec()` 组装 `Pipeline` → 帧循环驱动 `step()`（`compose()` 四模式为代码层兼容） | `umvp/pipe/test_composer.py`、`tests/test_police_uav_video.py`（脚本化 feed 风格） |
| 接线壳 | YOLO 推理出的 dets 喂进管道；VLM 的 infer 回调（真实远端/模拟）；告警/结果落盘上报 | `VLMAnalyzer.prepare()` + infer 回调（`composer.py`） |
| 测试壳 | 断言式测试 + 限帧 + 落盘可视化核验产物（annotated.png 级） | `tests/` 回归集 |
| 胶水文件 | 现有模块拼不出的新链路时，写新胶水文件（如坐标还原、原生分辨率出图） | `umvp/pipe/crop_restore.py`（约 200 行，零改动复用两模块） |

**关键先例**：`crop_restore.py` 就是一次"组装工"的完整工作样本——现有模块零改动，
新增 1 个胶水文件 + 1 个测试壳。组装工的行为准则就是把它**标准化、可重复、带建议和估价**地做出来。

### 3. 组装工的六类职能

#### 3.1 主职能：写壳代码

| 子项 | 做什么 | 产出 |
|---|---|---|
| 组装 | 把 spec 映射成 `compose()` 调用，选对四模式/链路阶段 | spec JSON + Pipeline 组装片段 |
| 驱动 | 帧循环（视频/摄像头/图集）+ `step()` 调用 + 背压（FrameManager 复用） | 驱动壳代码 |
| 接线 | YOLO dets 喂入、VLM infer 回调注入（真/假两种）、告警事件消费 | 接线壳代码 |
| 落盘 | 告警/报送结果落盘、可视化核验产物（画框图） | 产物目录约定 |
| 估算接入 | 壳里顺带调 `ResourceEstimator.estimate_pipeline`，交付时附资源报告 | 估算调用片段 |

交付物形态：**可运行的脚本 + 运行命令**，落在 `out/generated/`。

#### 3.2 配套职能：业务建议

| 子项 | 做什么 | 依据 |
|---|---|---|
| 需求解析 | 从业务描述提取：设备/分辨率/路数/目标类别/告警需求/预算 | 自然语言输入 |
| 链路选择 | 四模式（small_only/small_crop/small_full/large_only）或人脸链路或监控链路，讲清理由 | skill 决策表（P3 编写，**依赖项**） |
| 参数建议 | conf/iou/imgsz/frame_skip/check_interval/class_limits 等给初值并说明动机 | 决策表 + 实测指纹 |
| 预算反推 | 给定显存预算 → 建议 frame_skip / check_interval / 预期 FPS | `ResourceEstimator.back_calculate` |
| 方案对比 | 两个方案列成本与效果差异 | 估算报告 + 决策表 |
| 诚实边界 | 明确区分"已验证"与"需实测" | skill 诚实清单风格 |

#### 3.3 配套职能：链路效果测试

| 子项 | 做什么 | 参照 |
|---|---|---|
| 断言式测试 | 生成断言式测试壳（脚本化 feed / 真实输入两档） | `test_composer.py` 27 断言风格 |
| 真实推理烟测 | 限帧跑真实推理，确认链路通 | `tests/test_yolo_params.py`、`tests/test_police_uav_video.py` |
| 可视化核验 | 落盘画框图供目检（坐标映射等靠目检的项） | annotated.png 级产物 |
| 回归确认 | 交付前跑回归集全绿 | CLAUDE.md 常用验证命令 |
| 汇报 | 断言清单、通过/失败、**未验证场景清单** | skill 诚实风格延续 |

#### 3.4 配套职能：资源评估

| 子项 | 做什么 | 依据 |
|---|---|---|
| 静态估算 | 不加载模型，秒级粗估 | `ResourceEstimator`（P1 已落地） |
| 实测优先 | 有指纹用指纹，静态法只是粗筛 | `out/fingerprints.json`（`calibrate.py` 生成） |
| 链路聚合 | 按"每帧平均成本"聚合（VLM 节流折算、人脸嵌入命中后折算） | `estimate_pipeline` |
| 多路外推 | N 路数显存/帧率推演，超显存给 WARNING 并建议 frame_skip | `estimate_pipeline` streams 参数 |
| 换机提示 | 机器变化提醒重跑 `calibrate.py`，代码零改动 | CLAUDE.md 约定 |

#### 3.5 配套职能：基础系统介绍

| 子项 | 做什么 |
|---|---|
| 系统介绍 | 用户问"系统能干什么"时，通俗介绍 UMVP：四模块、四模式、人脸链路、web_lab、资源估算 |
| 模块答疑 | 单个模块/接口/参数怎么用、怎么测、在哪跑 |
| 现状边界 | 只讲已实现的能力，未实现的照实说"没有/未验证" |

> 这是"问答型"职能——输入是问题、输出是说明文字，不产生代码或文件。

#### 3.6 配套职能：VLM 提示词辅助撰写

| 子项 | 做什么 |
|---|---|
| 需求→提示词 | 从业务需求起草 `vlm_prompt` 初稿 |
| 词表对齐 | **提示词输出词表必须与 AlarmPolicy 的 `target_actions` 对齐**，一并给出 `target_actions` 建议 |
| 多版候选 | 给 2–3 版提示词（简洁/严格/带示例），说明取舍 |
| 验证建议 | 提示词需实测（真 VLM 或模拟 infer），标注"依赖实测" |

> 关键联动（代码依据）：`composer.py` 的 AlarmPolicy 按 `target_actions` **精确匹配**
> VLM 返回的 action 字符串——提示词若让模型自由发挥输出词表，告警命中率会归零。
> 撰写顺序必须先定词表、再写提示词。

### 4. 边界

#### 4.1 硬边界（绝不做）

1. **不改核心模块代码**：`umvp/pipe/composer.py` 四模块、`face_detect/`、`face_embed/`、`face_scan/`、`resources.py` 一律只读。必须改时先声明改动点与理由，**单独批准后**才动。
2. **不硬编码业务知识**：决策表、坑、指纹全在 skill + 指纹 JSON 里，agent 只读；skill 更新 = agent 能力更新。
3. **不跑无界推理**：限帧（max_frames）+ 超时 + 串行（复用 `_TEST_LOCK` 约定）；长任务先提示再跑。
4. **不把估算当实测**：静态法 vs 实测法误差 > 30% 标警告；未实测的场景只能写"未验证"，禁止写成已验证。
5. **不引入新依赖**：只用 ai conda 环境已有包（cv2/ultralytics/insightface/onnxruntime），不装新库。
6. **不写分支代码**：模式差异收敛为配置（"参数即配置、不写分支"是项目约定），不做任意 DAG（v1 链式）。

#### 4.2 软边界（要先跟用户确认）

1. **生成代码先展示再落盘**：先给方案说明 + 壳代码样例，确认后再写 `out/generated/`（文档先行）。
2. **新胶水 vs 改模块的判断**：优先零改动复用；判断要新增胶水文件时，说明成本（行数级）再动手。
3. **真实推理前提示**：YOLO 秒级、链路分钟级，跑之前告知预计耗时与限帧数。
4. **换机/换卡提示**：估算依赖本机指纹，机器变化提醒重跑标定。
5. **与 web_lab 分工**：agent 不做前端/交互层（那是 web_lab 链路设计器）；agent 只做智能层的"生成与验证"。

#### 4.3 v1 能力边界（先不做，写进文档防止承诺）

- 不发明新模块（只拼现有模块；缺能力时报告，不造轮子）。
- 不做任意 DAG 组装（只链式）。
- 不估算 VLM 远端推理延迟（本地只算素材准备，真实延迟标"依赖实测"）。
- 不做部署/运维/网络服务。
- 不做模型训练、不提供新权重。

### 5. 输入 / 输出 / 产物契约

**输入**（两种任选）：
- 业务需求自然语言：设备、分辨率、路数、要识别的目标类别、告警需求、显存/帧率预算。
- 已有链路数据库结构（`doc/数据库结构.md` §4/§5 的 pipelines/pipeline_steps）。

**输出交付包**（五件，缺一不算完成）：
1. 方案说明：选的链路 + 理由 + 参数初值（含与备选方案的对比）。
2. 资源报告：单模块 + 链路聚合 + 多路外推 + 预算反推建议。
3. 壳代码 + 测试壳（`out/generated/`）+ 运行命令。
4. 测试结果：断言清单、通过/失败、可视化核验产物路径。
5. **已验证 / 未验证清单**（诚实交付，缺这项不算完成）。

## 第二部分 详细流程

### 6. 一张图：需求从进来到交付

```
业务需求（自然语言 / spec JSON / 咨询问题）
   │
   ▼
[总装] 0 受理分类
   │  ├─ 咨询 / 系统介绍 ──► 直接答（读 L1 知识）──────────────► 结束（说明文字，无代码）
   │  ├─ 已有链路调参 ──► 定位 spec → 改参数 → 建议（告警/模式变化时需确认）► 结束
   │  ├─ VLM 提示词 ──► 先定词表 → 2-3 版候选 → 标注依赖实测 ──► 结束
   │  ├─ 改核心模块 ──► 升级通道（停住 → 说明改动点/理由/影响面 → 等单独批准）► 结束
   │  └─ 组装新链路 ──► 1 需求澄清 → 2 方案设计（闸门①：用户确认）
   ▼
[组装工] 1 解析 → 2 选链路 → 3 估算 → 4 写壳（先展示再落盘 out/generated/）
      → 5 测试 → 6 汇报
   │
   ▼
[总装] 5 质量门（不达标打回）→ 6 交付汇总
   │
   ▼
交付包 = 方案说明 + 资源报告 + 壳代码/测试壳 + 测试结果 + 已验证/未验证清单
```

组装类请求走"总装外圈 + 组装工内圈"；其余四类走分支直达结束。多链路 / 多子任务在总装
拆成多条组装任务，各自走组装工内圈，最后在总装质量门合并。

### 7. 各步骤详述

#### 第 0 步 触发与受理分类（总装）

| 分类 | 一句话定义 | 路由 |
|---|---|---|
| 组装新链路 | 把业务需求拼成可运行管道 | 进澄清 → 方案 → 派发 |
| 咨询 / 系统介绍 | 问系统能干什么、怎么用 | 直接答，不产生代码 |
| 已有链路调参 | 对已跑链路改参数 | 定位 spec → 改参数 → 建议 |
| VLM 提示词 | 改大模型研判的提示词 / 词表 | 先定词表 → 写候选 → 标依赖实测 |
| 改核心模块 | 要动 composer 四模块 / face_* / face_scan / resources.py | 升级通道（§10） |

边界情况：多意图夹带 → 按主导意图归类；信号不足 → 进澄清；已有 spec/产物 → 调参，没有 → 组装。

#### 第 1 步 需求澄清（总装）

一次问全，附示例值，减少往返：设备（RTX 3060 8G / 纯 CPU）、分辨率（1080p/720p）、路数（16 路）、
目标类别（人=0 / 车=2）、告警需求、预算（显存 8G、实时）、数据来源（视频流/图片/摄像头）。
产物：一段需求说明，缺项明标"未提供"。

#### 第 2 步 方案设计与闸门①（总装）

1. 读决策表 `L4/10-decision-table.md` 选链路；
2. 定参数初值（conf / iou / imgsz / frame_skip / check_interval / class_limits 等），说明动机；
3. 做备选方案对比（如 small_crop vs small_full 的成本与效果差异）；
4. 资源粗估：调 `ResourceEstimator` 静态层，对多路做外推，超预算给 WARNING 与 frame_skip 建议；
5. 写成方案书。

**闸门①（硬性）**：方案书完成后**停下，等用户确认**。未确认不进入下一步。
确认内容：选哪条链路 + 备选取舍 + 参数初值 + 预算可行与否。

#### 第 3-4 步 任务拆解与派发（总装）

- 单链路：直接派发组装工。
- 多链路 / 多子任务：拆成多条任务，逐条定输入（任务说明 + 验收口径）+ 输出（各自交付包）。
- 派发机制：【有工具时】调子 agent `pipeline-assembler`（或 Skill）；【无工具时】产出"任务包"
  （任务说明 + 组装工提示词或按 INDEX 内联的组装工所需分层文件正文），交下游消费方执行。
- 改核心模块需求不在此路径：停住，走 §10 升级通道。

#### 组装工实施（第 1-6 步）

组装工永远只管单条链路，每一步做完即停下汇报要点；长任务先告知预计耗时。

| 步 | 做什么 | 产物 |
|---|---|---|
| 1 解析 | 从任务书/业务描述提取六要素；缺啥问啥 | 需求要点 |
| 2 选链路 | 读 `L4/10` 决策表 → 落四模式或人脸/监控链路，给理由与参数初值；总装方案已定则直接落参数 | 链路选择 + 理由 + 参数初值 |
| 3 估算 | 【有工具时】调 `estimate_pipeline(spec, streams)`：单模块指纹 → 每帧平均成本聚合 → 多路外推 → 预算反推；【无工具时】给"待执行命令 + 预期产出"。每项标来源（静态/实测/依赖实测）；误差 >30% 标警告 | 资源报告 |
| 4 写壳 | **先展示方案再落盘**。壳代码四样：驱动壳 / 接线壳 / 测试壳 / 胶水文件（模板见知识库 `L3/07-shell-templates.md`）；确认后才写入 `out/generated/` | 可运行脚本 + 运行命令 |
| 5 测试 | 三段递进：①断言式测试（脚本化 feed，秒级）→ ②限帧真实推理烟测（提前告知耗时）→ ③可视化核验（annotated.png 级）；最后跑回归集（27 断言 + 人脸 7/7 自检）确认不破坏现有。全程串行（`_TEST_LOCK`） | 测试结果 |
| 6 汇报 | 五段式模板（方案 / 资源报告 / 测试结果 / **已验证/未验证清单** / 下一步建议）；没做的项如实标注"未做" | 交付包 |

#### 第 5-6 步 质量门与交付（总装）

**质量门口径三项，缺一打回**：①回归集全绿；②未验证清单诚实列全；③交付包五件齐全。
不达标 → 打回组装工，注明缺什么；达标 → 单链路直接汇总交付，多任务合并各子产物统一汇报。

### 8. 交互节奏总表

| 位置 | 触发 | 给用户看什么 | 决策权 |
|---|---|---|---|
| 总装 受理后 | 分类不明确 / 要素缺失 | 澄清问题清单（带示例值） | 用户回答 |
| 总装 方案设计后 | 方案书完成 | 链路 + 理由 + 参数初值 + 备选对比 + 资源粗估 | **用户确认（闸门①）** |
| 组装工 写壳前 | 壳代码骨架就绪 | 方案 + 代码骨架 | 用户确认后才落盘 |
| 组装工 真实推理前 | 要跑真实模型 | 预计耗时 + 限帧数 | 用户知悉（可中止） |
| 组装工 每阶段完成 | 一个阶段结束 | 该阶段要点 | 用户可纠正方向 |
| 总装 质量门 | 组装工汇报完 | 回归集结果 + 清单 + 交付包完整性 | 总装判定，用户最终验收 |
| 换机 / 换卡 | 环境变化 | 提醒重跑 `web_lab/calibrate.py` | 用户执行 |

节奏约定：**文档先行、验证闭环**（断言式测试，不接受"看起来对"）；每一步都是"小步汇报、可纠正"。

### 11. 走一遍：停车场拥堵检测需求

> 用 §6-§9 的流程把一条需求完整走一遍，作为阅读参照。

**用户**："我要做一个停车场拥堵检测的链路，16 路摄像头、1080p、8G 显存，堵了要告警。"

- **总装 0 受理**：组装新链路（有目标类别、告警需求、预算约束）。
- **总装 1 澄清**：确认帧率要求（实时）、拥堵判定口径（车辆数量上限 class_limits / 车辆静止超时）、目标类别 COCO 车=2。
- **总装 2 方案设计**：决策表对比——`small_crop`（YOLO 数车 + 拥堵片段裁剪送 VLM 研判）vs `small_only`（纯 YOLO 计数 + class_limits 判定，零远端依赖）。资源粗估：16 路外推显存超 8G → 给 WARNING + frame_skip 建议。方案书给出两案成本/效果差异。**闸门①等用户确认**。
- **总装 3-4 拆解派发**：单链路，派组装工，验收口径 = 交付包五件。
- **组装工 1 解析**：设备 RTX 3060 8G / 16 路 / 1080p / 车=2 / 拥堵告警 / 显存预算 8G。
- **2 选链路**：按确认的方案落 `small_only` 参数初值（conf=0.35 / imgsz=640 / class_limits="2:1,300" / check_interval=3.0）。
- **3 估算**：`estimate_pipeline(spec, streams=16)` → 单路显存/帧率 → 16 路外推 → 反推 frame_skip=2 时帧率与显存落到预算内。
- **4 写壳**：先展示 spec JSON + 驱动壳骨架（16 路帧循环）→ 确认后落盘 `out/generated/parking_monitor.py` + 测试壳。
- **5 测试**：脚本化 feed 断言通过 → 限帧真实推理烟测（告知预计耗时）→ 画框核验 → 回归集全绿。
- **6 汇报**：五段式交付包。
- **总装 5 质量门**：三项全过。
- **总装 6 交付**：交付包交用户，含"未验证场景"清单（如真实 RTSP 长稳未测）。

### 13. 验收标准（做成什么样算完成）

   内联相关层后，仅凭文本能产出可执行方案（工具步骤有"无工具"路径说明）。
