# qa-mechanism  (qa)

> 场景：一条链路里模块之间是怎么串起来的？一条帧进来之后数据是怎么一层层往后传的？
> 关注点：链路机制与数据流（总装须知）
> 采集：2026-10-13 15:50

## 总装工（architect）
_ok=True steps=2 tools=['read_doc']_

一条链路就是**多个模块头尾相接**，一条帧从最前面进来，被一层层加工、筛选，最后在尾部收成"事件"输出。下面按"一条帧的旅程"讲清楚。

## 一、串接的基本机制

链路 = **截取视频帧 → 识别模块逐帧产出「记录」→ 后续模块对记录做筛选/修改/事件生成 → 事件尾把事件收出来**。

设计链路时，只要想清楚三件事：**每段收什么、给什么、按什么顺序**。

## 二、一条帧进来后，数据分两条流一起往下走

每份「记录（Record）」都带着两部分一起向后传：

| 流 | 装什么 | 谁在上面干活 |
|---|---|---|
| **JSON 主干** | `frame_idx / ts` + 各模块陆续添加的字段（框、置信、类别、车牌号、人脸、身份、事件…），可序列化、可入库 | **筛选、修改、事件生成**都发生在这条主干上 |
| **图像旁路** | 原帧，以及各模块产出的目标子图、成品小图、画框图（不进 JSON，落盘才成图片） | **裁剪、标注**发生在这条旁路上 |

一句话记法：**筛选在 JSON 主干上，裁剪/标注在图像旁路上。**

## 三、模块对这两条流做四件事

| 动作 | 干什么 | 谁做 |
|---|---|---|
| **产出** | 往 JSON 主干加记录/字段（框、车牌、人脸、身份） | yolo / plate_recog / face_detect / face_embed / face_store |
| **筛选** | 只取舍、不改内容（同帧有效性 / 跨帧防抖） | det_filter / seq_filter |
| **修改** | 改内容；或在图像旁路上产出新图（子图、画框图） | vlm / target_crop / annotate |
| **事件生成** | 在记录上追加 `events`，链路尾收出来 = 链路输出 | det_filter / seq_filter（事件尾）+ vlm（经 publish） |

## 四、一条帧的典型旅程（举例）

```
frame_manager（放行原帧 + 记录骨架）
   │  图像旁路：原帧        JSON主干：frame_idx/ts
   ▼
yolo（读原帧 → 往主干加：框/置信/类别/track_id）
   ▼
det_filter（在主干上筛：留哪些目标、数量上下限；可标事件）
   ▼
seq_filter（跨帧防抖：连续多少帧/多久才算数；可作事件尾）
   ▼
target_crop（读原帧+框 → 旁路产出目标子图，喂二次识别）
   ▼
annotate（读原帧+框 → 旁路产出画框帧，喂 VLM）
   ▼
vlm（读画框帧 → 主干加研判字段 label/text）
   ▼
事件尾（det_filter.events / seq_filter.rules）→ 收出 events = 链路输出
```

## 五、两个关键点（设计时最容易踩）

1. **模块位置由"数据依赖"决定，不是固定编号。** 唯一固定的是 `frame_manager`（必首段且仅一段）；其余模块只要放在"能提供它所读那条流/字段"的模块**之后**即可。比如 yolo 只读图像旁路的原帧，接在任何产出原帧的模块之后都行，不必是第 2 段。整条链路的**最后一段**还须落在平台终段白名单内。

2. **结构即声明，图与图的衔接由平台壳固定编排。** spec 里放不放 `annotate`，就决定 VLM 看的是画框图还是原图；三条固定数据流（检测流 → 报送流 → 事件流）由壳编排，**不由阶段顺序驱动运行**，设计时零图像代码。
